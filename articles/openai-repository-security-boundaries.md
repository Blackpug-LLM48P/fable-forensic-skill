「OpenAIの内部リポジトリまで侵入した」という報告を見た。

それは大変だ。で、何に、どの権限で到達したのだろう。

モデル重みを持ち出したのか。研究コードを読めたのか。本番のデプロイ権限を取ったのか。このあたりが一緒になると、被害の話が途中から別の話になる。リポジトリという単語に、会社の全資産を詰め込まないでほしい。

ただ、この題をOpenAIの安全宣言と受け取られるのも困る。公開情報を読んで、到達点を確かめるための記事である。確認日は2026年9月18日。

## 入口は画像だった

Hacktronの原著によると、7月25日、フォーラムの画像処理に使われるlibheifの脆弱性からDiscourse環境でコードを実行し、OpenAI側のSSO不備を経由して社員のChatGPT／Codexアカウントへ到達した。接続済みのGitHub連携を使い、内部モノレポに検証用PRを作成したところで停止したという。内部コードを取得せずに影響を示した、と研究者は説明している。[原著：Hacking OpenAI](https://www.hacktron.ai/blog/hacking-openai)

入口の脆弱性はDiscourse側の公式勧告でも確認できる。CVE-2026-32882、画像アップロード経由のRCE、CVSSは8.8。修正版のDockerイメージと、画像処理の追加サンドボックスが案内されている。[Discourse公式勧告](https://github.com/discourse/discourse/security/advisories/GHSA-vhm9-85gw-x335)

フォーラムを侵害しただけで、通常は社員の別サービスまで使えるわけではない。今回の経路を読むなら、画像のデコーダと認証の接続部分の両方を見る必要がある。SSOの詳細な不備は公開されていないので、特定のトークン検証ミスだったとまでは書けない。

## ソースを読めることと、モデルを持ち帰ること

たとえば、コードにモデルの保存先が書いてあったとする。その文字列を読める権限と、保存先から重みを取り出す権限は同じではない。さらに、その重みを載せた本番環境を変更するには、別の認可が必要な構成もある。

これは構成例だ。OpenAIの内部がそのとおりになっている、という説明ではない。

モデル重みの保護を扱ったRANDの研究も、重みへのアクセス制限や監視、アクセス人数の削減などを個別に論じている。保護すべき資産を分けて考える根拠にはなるが、特定企業が対策を実装済みである証拠には使えない。[RAND：A Playbook for Securing AI Model Weights](https://www.rand.org/pubs/research_briefs/RBA2849-1.html)

PRも同じで、作成したことからマージや本番反映までを一足飛びには言えない。GitHubの標準権限でも、PRの送信とマージは別の操作として定義されている。[GitHubの権限仕様](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)

ここで「なら大したことはない」と安心するのは早い。ソースには実装上の知見がある。構成次第では、その先のシステムを調べる手掛かりにもなる。全部なくても、盗られて困るものはある。

なお、モノレポ内のフォルダ分けを、そのまま閲覧権限の分離と考えてはいけない。CODEOWNERSはレビュー担当や承認を管理する仕組みだ。別チームの担当フォルダだから内容を読めない、という保護ではない。[CODEOWNERSの仕様](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)

## この研究者たちは何者か

「少人数がAIを使って侵入した」と聞くと、AIを使い始めたばかりの誰かを想像するかもしれない。しかし、発見者側の経歴は省けない。

BeyondTrustはCVE-2026-1731の勧告で、Harsh JaiswalとHacktron AIへの謝辞を掲載している。OpenAMのCVE-2026-33439でも、公式勧告にRahul MainiとHacktron AIの名前がある。いずれも認証前のコード実行に関する報告だ。[BeyondTrust公式](https://www.beyondtrust.com/trust-center/security-advisories/bt26-02)、[OpenAM公式](https://github.com/OpenIdentityPlatform/OpenAM/security/advisories/GHSA-2cqq-rpvq-g5qj)

Mohan Pedhapatiには、2022年のElement Desktopについて、複数の不備を組み合わせた研究記事がある。こちらは研究者自身による公開記録として参照している。[Element Desktop研究](https://www.hacktron.ai/blog/element-rce)

熟練者が道具を使って作業を速めた事例から、初心者でも同じ結果になるとは導けない。どこを調べるか、失敗した結果をどう読むか。その判断を誰が担ったかも、AIの能力を評価するときの条件になる。

## 直ったのか、という問い

研究者の開示履歴では、OpenAI側の修正確認は7月25日。この件について修正が報告されている、と書くことはできる。[原著の開示履歴](https://www.hacktron.ai/blog/hacking-openai)

依存ライブラリについては、Debianが8月8日に対象CVEを含む更新を公開し、Debian 13の修正版を1.19.8-1+deb13u1としている。上流の番号が古く見えても、修正がバックポートされている場合がある。番号の大小だけでは判定できない。[Debian DSA-6417-1](https://lists.debian.org/debian-security-announce/2026/msg00328.html)

Discourseの勧告がDockerイメージの再ビルドを求めている点も読み落としたくない。アプリケーションを更新したつもりでも、実際に動く画像処理ライブラリまで入れ替わったかは確認が要る。

画像処理の防御には、不要な形式を扱わない、使用資源を制限するといった選択肢もある。ImageMagickはそのためのセキュリティポリシーを公開している。利用する形式と処理量に合わせて設定するもので、導入したという名前だけでは防御にならない。[ImageMagick Security Policy](https://imagemagick.org/security-policy/)

これらは修正と運用の話であって、OpenAI全体が安全だという評価ではない。公開資料からは、重みへの到達可能性や、当該PRから動くCIの権限までは分からない。

## いま打てる防御を、侵入経路に戻して考える

防御策を並べるだけなら、パッチ、MFA、最小権限で終わってしまう。運用では、その設定がどの操作を拒否するのかまで確かめたい。ここからは公開仕様に基づく防御設計の話であり、OpenAIの実装状況を説明するものではない。

### 画像を受け取る場所に、何を持たせるか

画像処理では、必要な形式だけを許可する方法がある。ImageMagickにはcoderやmodule、外部delegateを制限するポリシーがあり、メモリ、ディスク、処理時間などにも上限を設けられる。サービスでHEIFを使っていないなら、そのデコーダへ入力を渡す理由を見直せる。[ImageMagickの公式設定](https://imagemagick.org/security-policy/)

ただし、メモリ使用量の上限を設けても、メモリ破壊のバグそのものが直るわけではない。形式の制限、資源の制限、パッチ適用は、効く対象が違う。

私なら、変換処理が破られた場合の持ち物を先に調べる。画像の変換に、認証系の秘密、社内APIへの通信、本番データへの書き込みは必要なのか。必要がなければ、そのプロセスから使えない構成を検討する。これは今回の報告から導く設計上の提案だ。コンテナに入れた事実だけでは、権限や通信先を絞った証拠にはならない。

運用確認も、ビルドが成功したところで終えない。修正済みのイメージへ稼働中のワーカーが置き換わったか、古いワーカーが残っていないか、許可していない形式が実際に拒否されるか。更新手順と、更新後の状態を別々に見る。

### SSOの便利さを、権限の共有にしない

OAuthのセキュリティ指針であるRFC 9700は、アクセストークンの利用先を制限し、受け取るサーバーが自分向けのトークンか検証することを求めている。操作範囲を表すscopeも絞る。正しい署名があることと、そのサービスの操作に使ってよいことは別の検証になる。[RFC 9700 §2.3／§4.10](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.10)

漏れたトークンの再利用に備える仕組みには、mTLSやDPoPによる送信者への紐付けもある。ただし、トークンと鍵の両方が攻撃者に渡れば、その保護も弱まる。同RFCがこの限界まで説明している。今回のSSO不備が具体的にどれだったかは非公開なので、この対策一覧をそのまま原因分析に転用はしない。

「MFAを入れれば解決する」という説明にも抜けがある。NISTは初回認証と、その後のセッション維持を分けて扱っている。ログイン時に本人確認をしても、その後に利用するセッションの秘密が奪われる問題は残る。[NIST SP 800-63B：Session Management](https://pages.nist.gov/800-63-4/sp800-63b.html#session)

同文書では、IdPと各サービスのセッション終了は独立していること、アクセストークンがログインセッション終了後も有効な場合があることも説明されている。したがって、事故対応で「ログアウトさせました」と報告されたら、どのセッションとトークンを失効させたのかを確認する必要がある。認証基盤、アプリ、外部連携を一括で消したつもりにならない。

### PRを作れるアカウントから、どこまで動くか

PRとマージには権限の差がある。しかし、そこだけでは防御の説明が足りない。

GitHubは、信頼していないPRのコードを、強い権限を持つワークフローで実行する危険を明記している。特に`pull_request_target`や`workflow_run`と、未信頼コードのチェックアウトを組み合わせる場合が問題になる。self-hosted runnerについても、ワークフロー経由で環境が侵害される危険を警告している。[GitHub Actionsのセキュリティ指針](https://docs.github.com/en/actions/reference/security/secure-use)

PRの差分が本番ブランチに入らなくても、テスト用の実行環境が先にその差分を動かしているかもしれない。調べる対象はマージ履歴だけでは足りず、起動したジョブ、渡された資格情報、ランナーから届く通信先へ広がる。今回それが起きたという意味ではない。確認しないまま「PRだけだから無害」と結論づけられない、という話だ。

対策としては、未承認コードを実行するジョブのトークン権限を絞り、不要な秘密を渡さない。実行環境にも別の仕事の秘密を残さない。必要な権限だけをジョブごとに追加する方針は、GitHubの指針にも示されている。

本番デプロイの手前では、GitHub Environmentsの承認を利用できる。自己承認を禁止する設定もある。ただし、対応プランやリポジトリの公開範囲に条件があるので、自分の環境で使えるかを確認する。[Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)

承認者を置くだけで安心できるわけでもない。承認待ちの手前で危険なコードが実行されていれば、止める位置が遅い。何を実行する前に承認が要るのか、という順序まで設計する。

### 鍵を短命にするなら、発行条件も見る

GitHub Actionsからクラウドへ接続する際は、OIDCを使って短命な資格情報を取得する構成を採れる。長期キーをGitHubへ複製して置く必要を減らせる点が利点だ。クラウド側では、どのワークフローに権限を与えるかを条件で絞る。[GitHubのOIDC解説](https://docs.github.com/en/actions/concepts/security/openid-connect)

ここからは、その仕組みに対する運用上の評価になる。短命なトークンでも、不正なジョブが発行条件を満たしてしまえば取得できる。有効期間を縮める対策は、誰に発行してよいかという認可を代行しない。

監査で知りたいのは「何分ごとに鍵が変わるか」だけではない。どの主体が発行を要求でき、どの操作に使え、漏れた場合にどう止めるのか。その四つを追って初めて、ローテーションの効果を評価できる。

## 拡散された主張の、どこを反証するか

ここでは、提示された投稿の表現と、そこから派生しやすい解釈を区別する。以下の文言を、すべて特定の投稿者が実際に発言したという意味では使わない。また、原著の研究者自身の主張と、SNSで付加された解釈も同じ扱いにはしない。

### 「内部モノレポに到達した」から「全部抜かれた」へ

内部リポジトリに到達したという報告を、モデル重みや顧客データの持ち出しへ広げるには、追加の証拠が必要だ。対象資産の名前も、読み取り権限も、取得したという記録も示されていないのに、被害対象だけを増やしてはいけない。

ここで反証できるのは推論の飛躍であって、「持ち出しは絶対になかった」という反対の命題ではない。公開されていないものまで代弁する必要はない。

### 「三人でできたなら、国家ならどうなる」

提示された投稿には、少人数の研究チームの成功から国家主体を心配する問いがあった。この問い自体は妥当だ。RANDの重み保護研究も、機会的な攻撃者から高い資源を持つ国家主体までを区別している。[RANDの脅威モデル](https://www.rand.org/pubs/research_briefs/RBA2849-1.html)

ただし、その問いへの答えを「したがって国家はすでに全資産を取れる」にしてしまうと、証拠を飛び越える。攻撃者の能力が上がれば懸念は増す。それでも、どの権限境界を越えられるかは実装に依存する。人数を増やすだけの比例計算で侵害範囲は求められない。

国家主体を想定するなら、長期潜伏や別経路からの侵入も含めた評価が必要になる。今回の短い検証を、その評価の代わりには使えない。

### 「AIがやった」から「誰でもできる」へ

少人数であることは、経験が少ないことを意味しない。前述のベンダー勧告には研究者の実績が残っている。AIだけを主語にして、その条件を消すと読者は難易度を読み違える。

この一件からモデルの能力差を一般化するのも難しい。比較するなら、与えた資料、先行試行の成果、ツール、試行回数、人間の介入を揃える必要がある。公開された成功例は能力の存在を示す材料になるが、成功率や典型的な所要時間までは決めない。

### 「修正済み」から「もう安全」へ

この方向の飛躍も、同じ基準で扱う。

特定の脆弱性への修正は、その経路への対処を示す。組織全体についての無欠陥証明ではない。逆に、侵害が一件あったことをもって、すべての防御が無意味になったとも言えない。評価対象と期間を落とすと、どちらも印象の話になる。

今回の件で求めたい説明は「セキュリティを強化しました」より狭い。どの境界を直し、どの資格情報を失効させ、その状態をどう確認したか。そこまで出ていれば、運用者は自分の環境との違いを検討できる。

### 「PRを作っただけ」から「被害なし」へ

PRの作成は、正常な権限行使として処理された操作かもしれない。しかし、その指示元のアカウントが乗っ取られていれば、認証の前提が壊れている。アプリケーションが指示どおり動いたことは、正当な利用だったことの証明にはならない。

PRをマージしていない、研究者がコードを持ち出していない。この二点には意味がある。ただし、CIの挙動も権限も調べずに、侵害の影響をゼロとする材料にはできない。

反証を書く側も「煽りが大げさだから、実態は軽いはず」という推測に乗ってはいけない。元の主張から、資料が支える部分だけを残す。それで十分に批判になる。

## PRで止まった。その意味は

今回、特に気になるのは停止地点の読み方だ。

研究者が検証を止めた場所を、システムが侵入を食い止めた場所として扱ってしまうと、防御能力を過大評価する。検証していない先まで到達できたことにすれば、今度は被害を過大評価する。

記事を読む側として知りたいのは、次の三点になる。

| 確認したい対象 | 評価が変わる情報 |
|---|---|
| リポジトリ | 実際に読めた範囲と操作権限 |
| CI/CD | PRに反応する処理と、その実行権限 |
| 別の保護資産 | データや重みの保存先へ進めたか、その認可 |

この空欄を「きっと隔離されている」で埋める気はない。侵入先が本当にコアだったのか、という疑問は、コアを何と呼んでいるのかを決めて初めて調べられる。

リポジトリに全部あると思うな。

そこから先へ行けないとも、まだ言っていない。
